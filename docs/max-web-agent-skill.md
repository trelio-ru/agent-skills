# MAX runtime

Канонический source – `platform-skills/max-web/`. Signed package содержит только
runtime; DOM test dependencies в него не входят.

## Identity и запуск

Company/member/connection identity приходит только из проверенного package host
через `TRELIO_SKILL_COMPANY_ID`, `TRELIO_SKILL_MEMBER_ID` и
`TRELIO_SKILL_CONNECTION_ID`. Runtime проверяет также exact
`TRELIO_SKILL_ID=max-web` и корректную `TRELIO_SKILL_RUNTIME_VERSION` до выбора
локального каталога. Model-authored CLI-флаги identity не поддерживаются:
`--company-id`, `--member-id` и `--connection-id` отклоняются как неизвестные
аргументы и не могут выбрать другой локальный namespace.

Агент запускает только `runtimeExecution.localAction` и добавляет в
`parameters.arguments` команду и её обычные MAX-параметры. Секция `connection`
из `get_agent_skill` для обычного запуска не нужна.

Headed Chrome, включая login и assist, создаётся сразу неактивным через
host `startInBackground` (runtime >= 3.2.0). Host запускает dedicated persistent
profile без startup window, устанавливает provider guards и создаёт exact
background target с `focus=false`. Используется native viewport без изменения
window bounds. MAX не вызывает `bringToFront`; навигация, DOM click/fill,
snapshot и скачивание сохраняют OS focus. Пользователь сам выбирает окно для
ручного входа. Native app control, активирующий окно, допускается только после
прямой просьбы показать его; обычная recovery использует фоновые `assist-*`.
Создание foreground-окна с последующим hide/minimize/restore focus не подходит.

HTTP-код основной страницы проверяется общим host observer до UI/login и
сохраняется в safe diagnostics по [общему контракту](agent-skill-connections.md#http-диагностика-браузерных-навыков).
503 не запускает recovery reload, повторный QR/login или смену транспорта.
Для общих HTTP exports требуется host runtime >=3.4.0.

## Список и поиск

`dialogs --limit 100` без query перечисляет папку «Все» с bounded прокруткой
виртуального списка, не открывая переписку. Он возвращает `isUnread`, nullable
`unreadCount` и `coverage`. Счётчик папки может исключать muted-чаты и не является
общим числом непрочитанных. `complete=false` нельзя превращать в полный ответ.
Неизвестный UI или пустой список без распознанного empty state завершается ошибкой.

Строка home-чата имеет собственный heading; поиск использует отдельный cell/title/name
контракт. Папки, родительские listitem и вложенные кнопки не являются чатами.
Счётчики распознаются по специальным unread-индикаторам и семантическим aria-label,
включая русское «новое сообщение». Avatar badge, числа в адресе, дате или превью
не доказывают unread. Длинное превью не исключает чат. Неизвестный счётчик – null.

`dialogs --query` – bounded видимая выдача поиска, `contacts` требует query.
Одинаковые названия сохраняются для проверки неоднозначности. Только provider URL
позволяет объединить два результата без дополнительного доказательства identity.

`contacts --query` с явным международным номером (например,
`+79990000000`) использует отдельное действие MAX «Найти по номеру».
Номер нормализуется только для этого действия. Обычная строковая выдача по
названию не подтверждает телефон. Совпадение возвращается только после
загрузки канонического маршрута чата; явный отказ MAX возвращается как
`lookupState=not_found_or_private`, поскольку настройки приватности могут
запретить поиск по номеру. Неизвестная форма или неоднозначный результат
завершаются ошибкой, а не пустым подтверждённым списком.

`profile --chat` открывает один exact чат и его видимую панель сведений.
Телефон извлекается только из ссылки `tel:` или строки, явно помеченной
«Номер телефона»/«Телефон». Текст сообщений и список других чатов не являются
источником номера. Числовой маршрут может принадлежать и личному чату, поэтому
тип контакта не выводится из формы URL. Ответ различает `visible`, `not_visible_in_profile` и
неоднозначный/неопознанный UI. Открытие профиля остаётся пассивным чтением.
При exact URL имя не приходит из аргумента: сначала выбирается единственная
видимая кнопка с доступной подписью «Открыть профиль …». Для старых вариантов
MAX fallback выбирает только одну текстовую кнопку в верхней строке области
переписки, исключая боковой список и действия под заголовком. Неоднозначный
заголовок остаётся ошибкой.

Личное `Избранное` имеет зарезервированный официальный маршрут
`https://web.max.ru/0`. Runtime принимает exact название, `0` и URL `/0` как одну
identity. Текущий MAX SPA после прямой навигации к `/0` нормализует адрес к `/`
без выбора чата, поэтому runtime связывает маршрут с exact строкой
`title=Избранное, listIndex=0` папки «Все» и нажимает её один раз. После клика
identity подтверждают вместе маршрут `/0`, выбранная строка и заголовок
`Избранное – Сообщения для себя`. Глобальный поиск для этой identity запрещён:
он смешивает личный чат с одноимёнными публичными каналами.

## Стабильные ссылки и неоднозначность

Название, нормализованная `identity`, DOM `index` и одноразовый assist `ref`
не являются provider ID. При нескольких exact названиях обычный adapter
возвращает `MAX_CHAT_AMBIGUOUS` с bounded `candidates`, nullable URL/ID,
`candidatesComplete`, `finalMutationActionStarted=false` и готовыми
`recoveryArguments` для read-only `dialogs` assist. Список не выдумывает ID
из позиции строки. Этот код сразу разрешает осмотр кандидатов; три одинаковых
попытки не требуются. Worker при такой ошибке подготовки read-only операции
сохраняет поиск и сообщает `preparationIssue`, вместо завершения session.
Mutation с невыбранным адресатом остаётся закрытой.

Успешные `read`/`profile` и read-only `assist-snapshot` возвращают
`chatReference` фактически открытого чата: канонический URL, `stableId`,
nullable название, `verifiedAt`, `contextMatched`. Перед сохранением проверяются
официальный маршрут, готовая поверхность переписки и отсутствие смены route
во время чтения. Exact read дополнительно сверяет URL с результатом `openChat`.
Профиль/история, а не одно название строки, служат основанием выбора собеседника.
Canonical URL удаляет необязательный завершающий slash и нормализует `max.ru`
к `web.max.ru`; числовые ID групп сохраняют знак.

Owner-only `state/chat-references.json` лежит рядом с dedicated profile в
host-owned skill/company/member/connection namespace. URL является ключом:
тёзки сохраняются отдельными записями, старые названия остаются aliases.
Журнал содержит ссылки, bounded aliases, task refs, дату проверки и optional
owner-only locator телефона после успешного штатного поиска. Locator используется
только для повторного открытия того же exact URL, не выдаётся в knownChats и не
разрешает отправку; новый login очищает его. Сообщения, cookies и credentials
в журнал не попадают. Обычный profile
lock сериализует запись; unique exclusive staging и atomic rename не следуют
старому временно́му symlink. Symlink, неизвестная схема, лишние поля, unsafe mode
и повреждённый журнал возвращают `MAX_CHAT_REFERENCE_STORE_INVALID` без вывода
содержимого и без замены файла. Лимиты: 1000 чатов, 8 названий до 160 символов,
32 task refs до 512 символов на чат и общий 1 MiB; при обновлении удаляются
самые давно проверенные записи. Новый owner handoff `login` очищает только
этот журнал перед возможной сменой аккаунта. Скрытая смена аккаунта вне штатного
login не считается автоматически распознанной.

`dialogs` возвращает сохранённые ссылки отдельно в `knownChats`, не присваивает
их текущим строкам по имени и не объявляет их live coverage. Query фильтрует
aliases, `--context-ref` дополнительно фильтрует exact task URL. Этот optional
параметр принимает только HTTPS `trelio.ru/<company>/<project>/tasks/<number>/`
без credentials, query и fragment и разрешён только у `dialogs`, `read`,
`profile`. Он не меняет ACL задачи или MAX.

Только успешный exact `read`/`profile` с `--context-ref` закрепляет чат за
задачей. Assist discovery сохраняет URL без task binding, чтобы чтение двух
кандидатов не означало выбор обоих. Последующий `read`/`profile` по имени с тем
же task ref открывает единственную сохранённую ссылку до глобального поиска;
появление тёзки её не заменяет. Два закреплённых exact aliases возвращают
неоднозначность с их URL; ни один не перезаписывает другой. Без task ref журнал
не выбирает чат автоматически. Для mutation task binding не используется,
флаг отклоняется; адресат и полномочия подтверждаются обычным exact flow.

Агент после неоднозначности сам осматривает разрешённые кандидаты, получает
их ссылки из свежих снимков, останавливает assist и читает exact URL. Если
пользователь просит оба, читаются оба; если нужен один, контекст переписки
помогает выбрать и закрепить релевантный чат. Вопрос оператору нужен только
при неразрешённой смысловой неоднозначности после доступного осмотра.

## История и состояние чтения

`unread` читает содержимое выбранных непрочитанных чатов; для одних имён используется
`dialogs`. Ошибки отдельных чатов возвращаются вместе с `ok=false`, exit 2 и
неполным coverage. `watch` ограничен числом итераций и не исправляет сбой selector-а.

Ссылки групп поддерживают отрицательные числовые ID. Другие origin, credentials,
query и fragment в ссылках запрещены. История берёт одну внешнюю messageWrapper
на сообщение; вложенные .message и превью sidebar не становятся отдельными
сообщениями. Одинаковый текст без provider ID не дедуплицируется. Если DOM не
раскрывает ID, он остаётся null. Для `download` и других действий `--message-id`
принимает только непустой `providerMessageId` из свежего `read`; локальный
`messageKey` и `index` не являются provider identity. При отсутствии ID
`--target-text` получает весь возвращённый `message.text`, включая подписи
карточки файла, размер и время. `--target-author` добавляется только когда
`read` вернул непустой `author`; название личного чата не подменяет отсутствующее
поле. Единственное точное совпадение разрешает выбор без автора; несколько
одинаковых сообщений остаются неоднозначными. Ошибка выбора объясняет этот
порядок без ослабления переданных ограничений.
Длинные сообщения сохраняются. Deep link проверяет загрузку UI и один раз
перезагружает пустую SPA; URL сам по себе не доказывает открытый чат. Нераспознанная
пустая история возвращает ошибку, а не успешный пустой массив.

MAX гидратирует историю позже выбранной строки и composer-а. Runtime ждёт bounded
окно истории и возвращает `emptyState=favorites-empty` только когда exact `/0`
surface всё это время остаётся выбранной, обычные message wrapper не появились,
а composer и служебная карточка `Сохраните что-нибудь` уже видимы. Эта карточка
показывается и в непустом `Избранном`, поэтому сама по себе не доказывает пустоту
и не входит в `messages`. Текущий `data-bubbles-variant=outgoing` и
`messageWrapper--isOut` определяют исходящие сохранённые сообщения; их `meta`
используется как видимое время. `read` распознаёт цитату по явной reply/quote
разметке либо по отдельному блоку цитируемого отправителя внутри исходящего
сообщения. Для файла имя берётся из карточки; если
её class отмечает только иконку типа (`TXT`), допустимо имя с расширением из
видимого текста того же сообщения при наличии attachment control.

Индекс и selected-state строки могут находиться на самой интерактивной строке,
её контейнере либо внутренней cell – runtime проверяет весь exact `data-index=0`
row, не ослабляя связку с `/0` и заголовком личного чата. Текст служебной карточки
может содержать дополнительное пояснение. Нераспознанное состояние возвращает
только content-free признаки route/row/header/composer/control и число wrapper;
текст переписки, DOM, labels и screenshot в диагностику не входят.

Runtime блокирует READ_MESSAGE и READ_REACTION до проверенной отправки/ответа.
Имена отправителей можно проверить без открытия чатов; live smoke истории должен
подтвердить нулевое число forwarded read receipts и сохранение счётчиков после reload.
Тесты мутаций используют синтетические данные; реальные отправки требуют отдельного
разрешения адресата и содержимого.

Для отправки файла runtime сначала открывает видимый upload action MAX и ждёт,
пока каждое выбранное имя файла появится как новое вложение в черновике.
Отсутствие такого подтверждения возвращает `MAX_ATTACHMENT_NOT_STAGED` до
заполнения и отправки текста: частичная text-only отправка недопустима.
Текущий MAX показывает файл отдельным сообщением с кнопкой «Скачать», имя
которой может находиться в видимом тексте без `aria-label`. `download` ищет её
только внутри exact сообщения. Текущая кнопка открывает HTTPS GET к
`fd.oneme.ru`: обычный `download` и assist перехватывают только main-frame
navigation этого fixed origin от текущей страницы либо её непосредственного
popup. На время операции `window.open` только для exact HTTPS origin файлового
сервера направляется в `_self`: первая popup navigation ещё не имеет Frame,
а routed 204 оставляет MAX открытым. Другие цели `window.open` не переписываются;
при отсутствии проверенного initiating Frame загрузка прекращается. Ответ
получают через `route.fetch` того же browser context, без
redirect/retry; требуются HTTP 200, `Content-Disposition: attachment`, безопасное
имя и совпадение объявленного размера. Вместо передачи файла native download
manager Chrome runtime отвечает браузеру 204: временное окно можно закрыть
после сохранения. Signed URL, cookies, headers и body не входят в ошибки или
model-visible metadata. Другие origin, POST, subresource и чужое popup не
расширяют этот путь. Старые same-origin/blob карточки сохраняют native transfer;
после неясного результата второй transport не запускается.

Один вызов сохраняет один файл размером до 256 MiB в owner-only staging рядом
с output. Готовый файл с mode 0600 публикуется через exclusive hard link, поэтому
существующий либо параллельно созданный output не перезаписывается. При ошибке
staging удаляется. Успех требует завершённой записи, размера и SHA-256;
закрытие runtime ждёт pending transfer. Stop assist сохраняет тот же инвариант.
Быстрый ответ и панель эмодзи появляются при
наведении на exact сообщение; ответ находится справа от кнопки меню, а эмодзи
выбирается из проверенной панели над контекстным меню. Панель может содержать
ARIA-кнопки без нативного тега `button` и немного шире самого меню; проверка
требует восемь физических ячеек в одном ровном ряду, сворачивая вложенные
кнопки с одинаковой геометрией. Геометрия читается одним DOM-снимком:
последовательные Playwright `boundingBox` для части видимых ячеек возвращают
нулевые размеры. После открытия меню кнопки анимируются из нулевого размера;
runtime ждёт до 2,5 секунд ровно восемь готовых ячеек до нажатия. После
нажатия оно подтверждает появление положительного счётчика реакции в тексте
того же сообщения при неизменных содержимом и времени; эмодзи в MAX
отображается графикой и не находится поиском точного текста.
При несовместимости диагностика содержит
только ограниченное число и координаты соседних кнопок, без текста чата.
Пересылка в личное «Избранное» выбирает
строку `Избранное Сообщения для себя`, а не контакт с идентификатором `0`.
В сведениях группы кнопка карандаша доступна как «Показать настройки».
Удаление участника выбирает действие, явно обозначающее исключение участника из
чата, группы или беседы; фоновые действия удаления самого чата не подходят.
После подтверждения runtime повторно читает exact список и сообщает успех только
если выбранный участник отсутствует. Обычный клик по строке участника открывает
его личный профиль с действиями над контактом. Runtime наводит курсор на exact
строку в списке группы и принимает только выровненное с этой строкой меню
«Ещё». При отсутствии или двух таких кнопках выбор прекращается до изменения.
В меню exact строки MAX может показывать короткое «Удалить» без слова
«участник». Runtime принимает его только в этом единственном меню; после
действия требует подтверждения и повторно проверяет состав группы.
В больших группах `members` проходит exact прокручиваемый список ограниченным
числом шагов, собирает уникальные строки и сверяет результат с числом из
заголовка «Участники N», когда оно доступно. Неполный список заканчивается
`MAX_UI_UNSUPPORTED` и не подтверждает отсутствие бота; такое же полное чтение
предшествует добавлению и проверяет его итог. Вкладка с подписью «Участники N»
распознаётся как раздел участников, а не как строка переписки.
При неизвестной форме меню диагностика берёт только действия и листовой текст
этого меню, заменяет слова вне закрытого словаря на маркер и ограничивает их
число. Имена участников и произвольный текст в неё не попадают.
`chat-update` различает верхнее поле названия и поле описания по типу и
расположению, а после сохранения заново читает настройки exact чата. Пустое
`--description ""` очищает описание и входит в structural approval hash.

## Согласование отправки

Действует [единый контракт](agent-skill-connections.md#sending-authorization).
Company config не содержит разрешения отправки; старый `allowAutonomous`
объявлен deprecated. Runtime требует `--confirm` отдельного вызова; старый
локальный `autonomous` читается как `confirm`, `read-only` сохраняет запрет.
Разрешение оператора остаётся только в текущем разговоре с агентом.

## Браузер

MAX descriptor объявляет signed `browserSession` класса
`messenger-profile` с `manualAssist=true` и требует host 3.4.0. Общий host
выбирает системный Chrome/Chromium/Edge, устанавливает pinned Playwright, держит
absolute lease, profile lock и process cleanup. MAX adapter по-прежнему владеет
`web.max.ru`, passive WebSocket guard, selectors, exact-operation authorization
и проверкой результата.

Runtime сам запускает Chrome/Chromium с отдельным persistent
профилем выбранного подключения. Doctor/probe сообщают `dedicated-chromium` и
`sharedWithCodexBrowser=false`. Успешный probe подтверждает вход именно здесь.
Ошибка UI не означает отсутствие сессии и не разрешает повторный login или перебор
обычных браузеров. Неверные аргументы отклоняются до запуска браузера.

На медленном Windows bootstrap generic language/help controls могут появиться до
QR-панели. Runtime не считает такой shell готовым: он ждёт точный QR/phone-login
surface либо распознанный authenticated home. Незалогиненная страница возвращает
`MAX login is required` до проверки поля поиска; selector drift поля поиска
возможен только после положительного доказательства authenticated home.

Во встроенном Codex Browser сайт MAX открывается, но у него независимая авторизация.
Поддерживаемый Browser API не предоставляет WebSocket routing; попытка CDP
Page.addScriptToEvaluateOnNewDocument отклоняется как неподдерживаемая. Полноценное
пассивное чтение через эту поверхность не заявляется. Перенос cookies запрещён;
другая сессия требует явного выбора пользователя.

Для детерминированной несовместимости уже распознанного UI runtime возвращает
`MAX_UI_UNSUPPORTED`. Поиск участника, который не разрешил exact цель внутри
picker до финального действия, возвращает `MAX_PICKER_TARGET_UNRESOLVED` с
`finalMutationActionStarted=false`. Штатный `member-add` отдельно читает строки
модального списка участников. Официальный `https://max.ru/id…_bot` нормализуется
к поиску exact `@username`: текущая форма MAX не ищет полный URL. Когда строка
бота не содержит профильной ссылки, допускается только единственный результат
этого exact поиска с отдельной видимой пометкой «Бот» либо с ней в конце
названия. Такой результат может быть обычной `cell`-строкой внутри picker;
ячейки бокового списка чатов не участвуют в выборе.
Перед действием проверяется текущий состав, а после него – состав exact чата.
Текущий раздел «Участники» показывает людей как полноширинные кнопки под
«Добавить участников» и «Пригласить по ссылке»; строки переписки и бокового
списка не считаются составом. При отсутствии стабильного ID в строке нового
бота результат подтверждается только новым единственным совпадением его
отображаемого имени и увеличением числа видимых участников.
Ссылка на бота в сообщении не считается участником. Если результат добавления
не подтверждён списком, возвращается `MAX_MEMBER_ADD_UNVERIFIED` с
`finalMutationActionStarted=true`: нужен осмотр live membership до повтора.
Ошибка выбора сама по себе не доказывает запрет MAX на добавление ботов.

Read-only осмотр при `MAX_CHAT_AMBIGUOUS` доступен сразу по контракту выше.
Управляемая surface `assist-start/status/stop` также доступна сразу после exact
`MAX_UI_UNSUPPORTED` при отсутствии эффекта либо после трёх фактических
несетевых сбоев одной запрошенной операции в текущей работе. Для одного бота
можно считать независимо подтверждённые exact URL и `@username` в том же чате.
DNS, reset, сетевой timeout и HTTP 5xx не считаются; login, ACL, policy и
отсутствие подтверждения обрабатываются как условия доступа. Неоднозначную
mutation не повторяют ради трёх ошибок: сначала проверяют live membership.
Если бот уже добавлен, повтор не нужен. Если membership неясен, ручная session
`members` используется только для осмотра; `member-add` открывается отдельно
после проверки отсутствия бота и с прежним exact approval hash. Для других
mutation аналогично проверяется точный эффект до ручного изменения. Login
остаётся отдельным owner-handoff и не поддерживает assist.

Если бот не появляется или MAX отклоняет действие и в ручном окне, нужно
проверить настройку бота на платформе партнёров: [официальная справка MAX](https://dev.max.ru/help/chatbots)
указывает, что добавление в групповые чаты по умолчанию запрещено и включается
в настройках конкретного бота. Ошибка автоматического picker сама по себе не
доказывает эту причину.

Detached worker удерживает тот же dedicated profile и profile lock, устанавливает
passive WebSocket guard до первой provider navigation и поверх него синхронный
DOM-event gate. Для `probe`, `dialogs`, `contacts`, `profile`, `read`, `unread` и
`watch` gate работает в `read-only`: разрешает поиск, exact chat navigation и
scrolling, а для `contacts` – переход в раздел контактов, для `profile` –
заголовок уже выбранного exact чата. Gate блокирует composer, submit, settings,
создание чатов, downloads и mutations.
При выборе структурно распознанной строки чата gate проверяет саму строку или
канонический маршрут ссылки. Превью последнего сообщения входит в её accessible
label и может содержать «Отправьте», «Удалить» и другие слова действий; такой
текст не должен блокировать открытие чата. Отдельная кнопка действия без
заголовка чата остаётся за пределами навигации.
Для `members`, `download` и изменяющих команд gate работает в
`manual-control`: разрешает действия внутри `web.max.ru`, но блокирует внешние
ссылки, закрывает дополнительные окна и завершает session при off-origin
navigation.

Для exact `download` gate пропускает создаваемый MAX synthetic click по
временной ссылке `https://fd.oneme.ru` только при установленном attachment
transfer handler. Эта ссылка потребляется тем же проверенным transfer и не
открывает внешнюю страницу; другие origin, credentials в URL и остальные
операции не получают исключения. Блокировка DOM gate проверяется после
действия в обоих режимах и возвращает `MAX_ASSIST_ACTION_BLOCKED`, даже если
Playwright завершил click без исключения. После такой ошибки нужен свежий
осмотр live-state, а не автоматический повтор.

Download snapshot связывается с DOM-узлом exact выбранного сообщения, его
текстом, файловыми кнопками, их href/геометрией, route и viewport. Превью других
чатов, presence и story animations не входят в эту связку. Только file controls
получают refs; point должен попадать в ту же видимую кнопку без перекрывающего
элемента. Замена узла или исчезновение file controls возвращает
`MAX_ASSIST_DOWNLOAD_TARGET_CHANGED`, изменение текста/href/геометрии
инвалидирует старый снимок. Download не разрешает fill или клавиши кроме Escape.

Manual-control не создаёт второй контур полномочий. `assist-start` повторно
валидирует exact аргументы обычной операции. Каждая mutation требует `--confirm`,
локальная `read-only` policy продолжает её запрещать, а structural mutations
требуют неизменённый `--approval-hash` обычного `--dry-run`. SHA-256 exact
операции входит в session record; активную session нельзя переиспользовать для
другой операции. File chooser получает только exact заранее разрешённые
`--file`/`--avatar`; повторный chooser fail-closed. Download допускает ровно один
файл в новый exact `--output`, не перезаписывает существующий путь и возвращает
размер и SHA-256. Stop отказывается закрывать session, пока exact transfer ещё
выполняется. Запуск worker ждёт до 45 секунд: Chrome, home и exact чат загружаются
последовательно. Это окно не выходит за существующий абсолютный deadline.
После принятого stop клиент ждёт до 20 секунд положительного подтверждения
закрытия. Worker записывает owner-only terminal receipt в собственную UUID-папку
только после закрытия Chrome и освобождения profile lock. Живой PID Node не
отменяет это подтверждение; исчезновение записи, чужой UUID/PID и failed не
доказывают закрытие. Завершившийся процесс сохраняет прежний безопасный путь.
Receipt не содержит control token или port, не заменяет запись новой сессии и
удаляется при retirement exact session. Без подтверждения возвращается
MAX_ASSIST_STOP_UNCONFIRMED.

Текущий MAX descriptor использует host default 30 минут. Assist не создаёт
собственный срок: его `expiresAt` ограничен одновременно requested hold,
внутренним пределом MAX 30 минут и абсолютным host deadline. Session имеет exact UUID и
завершается через authenticated loopback control либо host/runtime timer. Bearer control
channel хранится только в owner-only local state и не возвращается модели. Агент
управляет уже открытым системным окном через native app/computer control или
локальные снимки и пошаговые команды внутри той же session. Для всех разрешённых
операций доступны `assist-snapshot/click/contextmenu/fill/key/scroll/point-click/point-contextmenu/point-scroll`;
read-only gate допускает поиск и навигацию, включая профиль exact чата и раздел
контактов в соответствующих командах; manual-control сохраняет
exact подтверждение операции. Для `members` worker открывает чат и детали,
а клики ограничены заголовком exact чата и разделом участников.
Снимок сохраняется и при незнакомой разметке панели: ответ имеет
`inspectionMode=visual`, пустые DOM refs и неполное `coverage`. Модель читает
локальный PNG и может вызвать `assist-point-click` только для заголовка exact
чата или семантически проверенной вкладки «Участники», либо
`assist-point-scroll` по выбранной точке
видимого списка. Координаты соответствуют CSS-пикселям PNG. Runtime повторно
сверяет chat route, viewport, возраст snapshot и допустимость цели; координаты
не разрешают менять состав группы или отправлять сообщения.
Подтверждённые `member-add` и `create-group` также используют
пошаговые команды в той же fenced session. Для
`member-add` worker до передачи управления открывает exact чат и picker и
ограничивает дальнейшие действия его provider route. Snapshot возвращает локальный
owner-only PNG и максимум 100 видимых элементов активной формы, без cookies и
CDP endpoint. Фоновые обновления списка чатов не делают снимок модальной формы
устаревшим; перед точечным действием повторно сверяется его видимый элемент.
Широкую форму runtime связывает с наименьшим видимым модальным контейнером,
где находятся и поиск, и финальная кнопка. Фоновые обновления бокового списка
не меняют её хеш; при изменении формы во время screenshot выполняется до трёх
попыток пассивного снимка. Любое действие требует полного совпадения
свежего снимка. Вложенная область списка внутри модального окна не отсекает нижнюю кнопку
«Добавить» из точечных controls. Screenshot удаляется при stop и при
retirement session. Ref и UUID снимка привязаны к хешу содержимого и геометрии,
живут две минуты и расходуются перед действием, поэтому неизвестный ответ не
позволяет повторить click. Нельзя выбирать строку без доказанной identity бота.
`MAX_ASSIST_SNAPSHOT_STALE` и pre-action `MAX_ASSIST_TARGET_INVALID` возвращают
`actionApplied=false`, `recovery.command=assist-snapshot`, `reselectTarget=true`
и `automaticReplay=false`. При известном UUID session ответ содержит exact
`recoveryArguments` для её свежего снимка. Агент заново выбирает цель по этому
снимку; старые refs/координаты не переносятся и прежний click не повторяется
автоматически. Признак относится только к отвергнутому шагу, не ко всем прошлым
действиям session. Ошибка после начала mutation или потерянный ответ требуют
проверки exact live state до возможного повтора.
Для `members` хеш снимка привязан к exact панели, вкладке, геометрии и позиции
её списка. Обновление превью в боковой панели и присутствия отдельных людей
не делает прокрутку устаревшей. Прокрутка меняет только найденный контейнер
участников; после неё требуется новый снимок. Если весь короткий список
помещается без прокрутки, действие завершается без перемещения только при
наличии строк той же панели; если заголовок содержит число, оно обязано совпасть.
Вкладка без числа допускает только визуальный осмотр и не доказывает полноту.
Отсутствие опознанной панели переводит снимок в visual inspection. Явное
несоответствие счётчику не подтверждает полноту списка. Визуальная прокрутка
также не доказывает отсутствие участника без сверки снимков от начала до конца.
Остальные операции с указанным чатом заранее открывают его в той же session;
действия над сообщением раскрывают меню exact сообщения, `forward` дополнительно
открывает окно выбора адресата, а `chat-update` – форму настроек группы.
Их снимок доступен для диагностики, но точечные in-session
click/fill/key/scroll остаются запрещены: выполнение требует адресуемого native
окна и прежней exact authorization. Штатное создание группы
распознаёт доступное имя кнопки «Начать общение», пункт «Создать группу» и
финальную кнопку «Создать». Если MAX не находит полное имя участника, поиск
сужается до первого слова и выбирает только единственную строку с полным
именем и распознанным суффиксом присутствия.
Чтение состава принимает
только строки раздела участников в деталях чата и ошибкой сообщает о
неопознанном разделе. Новую вкладку, Codex Browser
и перенос cookies не используют. Перед действием агент проверяет exact
`interactionMode`, установленный gate и для mutation
`mutationAuthorized=true`, выполняет только разрешённую операцию, проверяет
live-state и всегда вызывает exact `assist-stop`. Неоднозначную mutation нельзя
повторять автоматически. Результат визуального осмотра остаётся bounded visible
evidence и не доказывает полноту или стабильную identity.

Воспроизводимый дефект `MAX_UI_UNSUPPORTED` или guard/runtime fallback можно
передать только через штатный Trelio public-feedback proposal flow: сначала
public-safe `search_public_product_feedback`, затем при отсутствии дубля
`render_public_product_feedback_proposal`. Окончательная публикация остаётся
действием оператора в App. В public title/description запрещены private названия
компании, проекта, задачи, чата и контакта, тексты сообщений, local paths, session
UUID, cookies, credentials, DOM и screenshots; допускаются обезличенные command,
public error code, expected/actual behavior и steps. Без App прямого способа
публикации нет.

`bootstrap` устанавливает только platform-independent `playwright-core@1.60.0`,
но не скачивает Playwright Chromium. На Windows, включая ARM64, runtime запускает
найденный `npm-cli.js` текущим `process.execPath` без `npm.cmd`, `cmd.exe` и shell;
`cwd` фиксирован на приватном runtime-каталоге. Для browser process используется
установленный Chrome, а при его отсутствии – штатный Microsoft Edge. Поэтому
архитектура браузера определяется самой системной установкой, а не x64 browser
artifact Playwright.

Ошибка bootstrap имеет code `MAX_BOOTSTRAP_FAILED` и bounded diagnostics:
очищенные пути Node/npm, argv, cwd, exit code, child `error.code`, signal и хвосты
stderr/stdout. Домашний каталог, credentials в URL и npm auth/token values
редактируются до JSON-ответа. Отсутствующий npm CLI и недоступный runtime-каталог
возвращают отдельные `MAX_NPM_CLI_NOT_FOUND`, `MAX_NODE_EXECUTABLE_INVALID` и
`MAX_RUNTIME_DIRECTORY_UNWRITABLE`.

## Госключ

`read`/`send` принимают exact официальный deep link
`https://max.ru/goskey_bot` и его browser canonical
`https://web.max.ru/goskey_bot`. Другие произвольные top-level handles,
credentials, query и fragment запрещены. Открытие требует сохранения exact
canonical route и готовой поверхности чата; неизвестный numeric redirect
fail-closed. Открытие не нажимает «Начать» и не запускает bot callbacks.
Полный рабочий flow и ссылки на первичные источники находятся в
[SKILL.md](../platform-skills/max-web/SKILL.md#госключ-через-max).

Поддержка deep link не означает поддержку всех кнопок бота. Отправка документов
использует существующий exact `send --file ... --confirm`, получение –
проверенный `read`/`download`. Успешная доставка файла не доказывает
создание заявки на подпись. Неизвестный результат запрещает второй маршрут;
human phone signature и ГОСТ validation остаются отдельными этапами.
Выбор Госуслуги/MAX разрешён только formal operation routing supporting releases,
без совместного профиля и фиксированного приоритета.
