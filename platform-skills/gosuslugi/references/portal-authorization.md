## Авторизация

1. Используй один выделенный runtime context и продолжай действие в той же сессии после ЕСИА.
2. По умолчанию выбирай роль физического лица; организацию – только по прямой просьбе.
3. Обычные password/TOTP формы проходит только защищённый runtime. При неизвестной форме он останавливается для человека, не угадывает поле пароля и не делает повторную отправку после неизвестного результата.
   На штатном QR-экране с единственной видимой кнопкой «Логин и пароль» runtime сам выбирает парольный вход, даже когда ниже перечислены биометрия и другие способы. Это действие лишь меняет способ входа; отдельные CAPTCHA, push/SMS, неподдерживаемое согласие и выбор личности остаются ручными. Стандартное согласие ЕСИА в делегированном входе проходит runtime по сценарию `esia`.
4. Не меняй сетевой маршрут автоматически. Transport failure не доказывает неверный пароль, потерю сессии или необходимость повторного setup. У нового runtime нет proxy/headless/plaintext fallback.

При `auth_submit_ambiguous` обычного портала и живом `authRecovery=resume_available`
сразу выполни возвращённый `resume` той же сессии без вопроса пользователю.
Затем проверь `wait`/`status`: сохранённые sent-флаги исключают повтор уже
выполненного ввода/submit. `resume_exhausted` останавливает автоматический цикл.
Ошибка выбора кнопки сама по себе не доказывает отказ credentials или challenge;
для failed внешнего authorize этот переход не применяется.
