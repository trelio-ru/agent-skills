## Произвольные Playwright-сценарии и ЕСИА

В этом режиме вызывающий агент получает обычные `context` и `page`: разрешены произвольный Playwright-код, переходы, формы, upload/download и работа с несколькими сайтами в пределах поручения. Отдельный навык браузера не нужен. Госуслуги обслуживают только ЕСИА; процедуры внешних сайтов остаются в сценарии агента или профильном навыке.

1. Через exact verified runtime выполни `client`. Он вернёт `modulePath`, `guidePath` с полным примером, nonsecret `options` с company/member и `configHome`. Прочитай `guidePath`. Импортировать клиентский модуль разрешено **только по этому пути из текущего проверенного пакета**, без исходников репозитория, старого кеша и смены identity.
2. Обычными средствами Playwright создай отдельный headed browser с непостоянным context и открой публичную страницу нужного сайта. Не копируй cookies из другого браузера, не используй plaintext persistent profile или `storageState({path})`. Выполни нужные публичные шаги сценария до штатного входа. Если кабинет уже доступен, новая авторизация не нужна.
3. После проверки разрешения на вход создай `createEsiaAuthorization(page, { ...options, configHome, origin: "https://нужный-сайт", confirm: true })` **до** нажатия штатной кнопки входа. Затем сценарий сам нажимает эту кнопку. Не конструируй OAuth URL. Помощник наблюдает реальный запрос ЕСИА в той же странице либо в новом direct popup с exact исходной Page как opener и связывает его с точным HTTPS callback/state из этого запроса. Список внешних сайтов, callback-хостов и маршрутов кабинета не нужен: внешний broker/SSO и дальнейший сценарий остаются у вызывающего агента. Начатая до helper-а transaction не восстанавливается задним числом. Уже открытое, чужое, вложенное или второе окно не принимается. Не создавай второй helper на popup; исходная форма и файлы сохраняются. Клиент запускай из обычного живого Node.js caller; VM `node_repl` может импортировать его, но упасть с `process is not defined` при вызове. Не подменяй globals; управляющий канал caller проверь до входа.
4. В пошаговом caller сразу создай `observeEsiaAuthorization(login)` и выведи request отдельным `login.request.then(...)` с обработкой ошибки. **Не жди `login.request` или `login.authenticated` внутри очереди browser-команд:** обработчик заканчивается после click; `state` и следующий разрешённый click остаются доступны. Первая кнопка может открыть только modal, а ЕСИА – вторая кнопка в нём. `observer.snapshot()` сразу возвращает `esia_request_pending`, через 15 секунд без запроса – `esia_request_not_observed`. Тогда проверь промежуточную публичную страницу в той же Page/helper и выполни наблюдённый следующий шаг в пределах поручения; не продолжай пустые polls, не пересоздавай helper и не объявляй ручной challenge без фактов. Это диагностический срок, не отказ/отмена авторизации. `esia_authorization_required` содержит `request` с IDs, origin, сроком и массивом `arguments`: передай массив **тому же verified runtime Госуслуг**. Пока `authorize` выполняется, caller остаётся живым. В stdout выдавай только этот request и безопасное состояние; auth DOM, URL/code/state, cookies, credentials и сетевые тела не выводи. Полный пример – `guidePath`.
   Если обычная сессия Госуслуг уже находится в `ready`, `authorize` сам передаёт exact запрос её worker-у: не останавливай сессию, не запускай вторую и не проси новый Touch ID/пароль ОС. Worker использует уже разблокированный vault только для одной проверенной transaction, сохраняет текущую страницу Госуслуг и после callback возвращается в `ready` с `authorization.status=callback_verified` и точными origin/request IDs. После потери помощника он возвращает `authorization_failed`, сохраняя результат попытки; отдельный портал может оставаться доступным. Отдельно напоминать агенту «используй вход через Госуслуги» не нужно: профильный сценарий и разрешение на вход уже определяют этот маршрут.
5. `await login.authenticated` возвращает `{ context, page, serviceResponse }` – те же исходные объекты после проверенного ответа ЕСИА и document commit внешнего callback либо его exact HTTP redirect chain. `serviceResponse` содержит только `httpStatus`/`httpOrigin` этого документа. Навык прекращает наблюдение сразу после возврата: дальше агент управляет браузером сам. Параметры/токены, которые внешний сайт добавляет в своей HTTP redirect chain, не являются новой transaction ЕСИА. Ошибка внешнего сайта, в том числе HTTP 401/403/503 на callback, передаётся агенту через `serviceResponse` и не становится отказом ЕСИА. Это **не** proof входа в кабинет: свежей рабочей страницей отдельно проверь результат сайта и только затем сообщай «вход выполнен». Не повторяй ЕСИА ради ошибки сайта. Если принятый callback ещё ведёт на `roles.gosuslugi.ru`, runtime один раз выбирает единственную карточку физлица и ждёт внешнего document return. Popup может закрыться сам; закрытие или postMessage без callback/state и document commit не доказывают возврат. SMS/push, CAPTCHA, согласие и подпись проходят по прежним правилам в связанном окне; при необходимости используй `status`/`resume` exact auth-сессии без повторного ввода после неизвестного результата.
6. В `finally` вызови `login.close()`, затем закрой только созданный сценарием context/browser. Закрытие помощника не закрывает браузер и не стирает подготовленную форму. Доступ помощника к сохранённым credentials ограничен native deadline не больше 30 минут; жизненным циклом и рабочими данными внешнего браузера управляет вызывающий сценарий.

Пароль и TOTP seed остаются в прежнем encrypted vault; seed/key не передаются клиенту. Текущие login/password/TOTP проходят через приватный канал в RAM доверенного сценария. Полный Playwright context технически позволяет читать cookies, наблюдать сеть и поля входа: это сознательно открытый доступ к браузеру, а не прежняя изоляция auth от кода сценария. Не возвращай эти данные модели и не записывай их в файлы/логи. Произвольный код не является разрешением на подачу, подпись, платёж или передачу данных.

Пример последовательности и владение процессами – [Playwright-клиент](playwright-client.md).
