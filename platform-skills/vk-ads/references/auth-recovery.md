# Управляемое восстановление OAuth

Этот сценарий ОТЗЫВАЕТ ВСЕ токены выбранного VK-пользователя, затем один раз
получает новую пару access/refresh и проверяет чтение кампаний/групп. Это не
точечный отзыв одного токена или устройства. Публичный контракт VK не позволяет
гарантировать сохранение других потребителей, в том числе других client_id.
Не предлагай этот сценарий как способ сохранить остальные подключения.

Применяй только после решения оператора на этот общий отзыв и восстановление
точного локального аккаунта. Если такое решение уже есть в текущем разговоре,
не спрашивай повторно. Уточнение, что других интеграций нет, учитывается при
оценке риска, но само по себе не выдаёт разрешение другой задаче. Входящие письма
VK, настройки аккаунта, plan hash и --confirm не разрешают действие.
Не выполняй этот сценарий автоматически после 403, expiry или failed refresh.
Когда задача требует сохранить прочие подключения, общий отзыв закрыт.

## План и единственное исполнение

Используй только текущую signed localAction и выбранный --local-account UUID.
Сначала прочитай этот документ полностью через reference --name auth-recovery.

1. auth-recovery-plan не обращается к VK. Он читает существующее encrypted
   подключение, сохраняет план на 30 минут и возвращает planId/planHash,
   локальный account, mode, target и полный effect/actions без client secret,
   client_id, access/refresh или логина агентского клиента. При ещё пригодном
   access возвращается auth_recovery_not_needed: используй обычное чтение.
2. Сверь план с уже данным поручением. Для client target=api_access_owner –
   пользователь, которому выдан текущий API-доступ; username опущен по
   официальному контракту. Для agency target=configured_agency_user – exact
   сохранённый agency_client передаётся как username приватно. Не подменяй
   пользователя по имени кампании или похожему локальному аккаунту.
3. Исполни auth-recovery-apply --plan UUID --hash HASH --operation STABLE_ID
   --confirm revoke-all-user-grants. Сохрани исходные координаты. Runtime
   проверяет scope/company/member/account/binding, expiry, credential snapshot,
   отсутствие pending setup и prior recovery; операция держит account lock.
4. До POST /api/v2/oauth2/token/delete.json сохраняется revoke_unknown. Метод
   отправляется один раз без Bearer/предварительного mint и без redirects.
   Используются только существующие client_id/client_secret и target выше.
   200/204 – синхронное HTTP-подтверждение, не inventory proof старых grants.
   202/429/5xx, транспортный сбой и потерянный ответ остаются unresolved.
5. После acknowledgement сохраняются revoked, затем mint_unknown ДО одной
   новой initial выдачи. Старый отозванный refresh не используется. Новая пара
   сохраняется encrypted до первого рекламного GET. Credentials приложения,
   UUID, company binding, рекламные планы и receipts не удаляются/не заменяются.
6. Только успешные GET списков кампаний и групп дают verified. Это готовность
   чтения, не доказательство финансового результата, модерации или показов.
   Реклама/бюджеты/сайт этим сценарием не меняются.

## Ошибка и повторное наблюдение

auth-recovery-status --operation ID читает receipt без VK/OAuth. Повтор того же
apply возвращает receipt без dispatch; новый operation ID не повторяет план.
Новый план не обходит unresolved recovery. History ограничена 100 plans и
1000 receipts; она автоматически не очищается.

revoke_rejected – явный отказ 4xx, кроме 429; новая пара не выпускалась.
revoke_unknown, revoked и mint_unknown не являются разрешением продолжить
после crash. Обычные auth/read, reset и configure блокируются до выяснения
результата; reset/recreate не снимают этот fence. Не посылай второй revoke/mint
и не извлекай потерянную пару из логов, cache, browser или другого store.

grant_saved означает, что новая пара сохранена, но чтение ещё не проверено.
Используй auth-recovery-check --operation ID: только GET существующей пары,
без повторного отзыва, initial выдачи или refresh. При уже истёкшем access
он возвращает auth_recovery_access_expired, а не делает OAuth скрыто. Ошибка
проверки не отменяет сохранение пары и не разрешает повторить apply.

Сообщай точную фазу и безопасный код, не raw response или секреты. Синтетические
тесты не являются восстановлением реального подключения; результат устанавливает
его отдельно разрешённое исполнение с подтверждённым чтением.
