Для `edit`, `delete`, `forward`, `create-direct`, `create-group`, `member-add`,
`member-remove` и `chat-update` всегда сначала запусти неизменённую команду с
`--dry-run`, покажи exact payload, затем повтори с
`--confirm --approval-hash HASH`. Это требует отдельного подтверждения оператора. После
неоднозначной mutation сначала перечитай live-state и не повторяй вслепую.

## Рабочий порядок

- Сначала запусти `doctor`; при отсутствии browser runtime – `bootstrap`.
  `probe` проверяет UI без текстов чатов, cookies или credentials.
- Для первого входа открой `login --headed` и скажи дословно:
  `После входа в MAX закройте окно.` Закрытие завершает owner handoff, но не
  подтверждает сессию. После `window_closed`, `hold_expired` или ошибки
  закрытой page/context сразу выполни один свежий `probe` в новом browser
  process. Только probe подтверждает сохранённую авторизацию; не повторяй
  `login`, пока probe явно не потребовал вход.
- Перед исходящим сообщением прочитай 5–10 содержательных реплик exact диалога
  и сохрани обращение, `ты/вы`, формальность и тон. Прямая инструкция
  пользователя приоритетна. При проверенном `direct-chat-empty` прошлых реплик
  для оценки тона нет; используй указания пользователя и контекст текущего
  обращения, не запускай fallback ради поиска отсутствующей переписки.
- Навык сам запускает Chrome/Chromium с отдельным persistent-профилем MAX.
  Окно с первого запуска остаётся в фоне: login, assist и автоматические
  действия не забирают фокус. Для ручного входа пользователь сам выбирает
  окно; агент не вызывает `bringToFront` и не активирует приложение без прямой
  просьбы показать его. Для фоновой работы используй встроенные `assist-*`.
  Он не разделяет сессию со встроенным браузером Codex или обычным профилем
  Chrome. Успешный `probe` уже подтверждает вход: не ищи его в других браузерах.
- Незалогиненная сессия возвращает exact `MAX_LOGIN_REQUIRED`: выполни обычный
  `login --headed`, а не browser fallback. Детерминированная несовместимость
  распознанного UI возвращает exact `MAX_UI_UNSUPPORTED`. Ошибка
  `MAX_PICKER_TARGET_UNRESOLVED` означает, что поиск участника остановился до
  финального добавления; это не доказывает, что MAX запрещает добавлять ботов.
- Для штатного `member-add` используй официальный адрес
  `https://max.ru/id…_bot` или exact `@username` бота. Runtime ищет бота в
  модальном списке участников, сверяет идентификатор до нажатия «Добавить» и
  после действия перечитывает состав exact чата. При неясном составе возвращает
  `MAX_MEMBER_ADD_UNVERIFIED`: сначала проверь список, прежде чем повторять.

## Управляемый browser fallback

Signed runtime включает `manualAssist=true`. Это сохраняет существующий ручной
fallback MAX поверх общего host browser-session layer: он открывается в том же
dedicated profile, наследует тот же абсолютный deadline и не получает отдельной
mutation authority.

Неоднозначность `MAX_CHAT_AMBIGUOUS` сразу разрешает read-only осмотр
кандидатов; это обычный выбор чата, без повторных попыток и mutation. Если
подготовка `assist-start --fallback-for read/profile` встретила тёзок, worker
сохраняет окно поиска с `preparationIssue.code=MAX_CHAT_AMBIGUOUS`: продолжай
осмотр строк в той же session.

Read-only gate разрешает штатную кнопку «Найти по номеру» в поиске главной
страницы, чтобы cold контакт открывался и при подготовке `read/profile`.
Неизвестный результат поиска возвращает `MAX_UI_UNSUPPORTED` с
`reason=phone-lookup-outcome-unverified`; worker сохраняет защищённое окно
с `preparationIssue` для осмотра. Это не подтверждение адресата или пустой
истории; произвольные кнопки, composer и отправка остаются заблокированы.

Используй fallback после exact `MAX_UI_UNSUPPORTED` при доказанном отсутствии
внешнего эффекта. Также разрешён fallback, когда одна запрошенная операция
навыка три раза завершилась несетевой ошибкой. Считай три фактических сбоя в
текущей работе; для выбора одного бота засчитываются его независимо сверенные
exact ссылка и `@username` в том же чате. Не требуй четвёртой попытки и не
повторяй mutation с неизвестным результатом ради счётчика. Ошибки DNS,
соединения, сетевого timeout и HTTP 5xx не засчитываются. Отсутствие входа,
прав, локальная `read-only` policy и невыданное подтверждение – условия доступа,
а не сбои навыка; их решай штатным путём.
